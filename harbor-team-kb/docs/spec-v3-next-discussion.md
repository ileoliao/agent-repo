## 1. 调查结果如何成为团队记忆

### 已记录的更新事项

- 在任务结束或阶段性交接时，由 Agent 提出可审阅的“团队认知变更”：新增了什么、纠正了什么、依据是什么、适用范围是什么、还有什么未知。
- 本次任务的完整调查笔记与长期共享记忆分开；原始源码、日志、需求和运行数据保留在各自载体，卡片保留必要解释与引用。
- 优先更新已有业务入口、关系、契约与经验；确有新概念或可复用判断时再新增，避免一任务一卡和新旧结论并存。
- 明确区分当前行为、计划变更与实际生效范围，不能把未合入或未部署的新行为写成普遍现状。
- 共享记忆经适当责任方审阅后进入私有数据仓；后续任务沿入口读取并重新核实适用性。

### 接口业务变更示例（非真实项目事实）

取消订单由同步退款改为异步退款后，可能需要更新：

1. 订单、支付、账务之间的业务关系及调查入口。
2. “取消受理”与“退款完成”的语义区别、适用版本和证据。
3. 调用方、事件消费者和对账任务依赖的时序假设。
4. 退款延迟的排查路径与必要测试；未证实的影响继续标为未知。

### 当前实现与待补能力

- 已有：`propose` 草稿、`validate` 校验、`publish` 私有仓 PR、来源锚点状态、显式指纹复核、争议草稿。
- 待设计和实现：调查结束时主动提炼认知变更、选择新增或更新目标、识别冲突和关联更新、向用户呈现有依据的差异。
- 自动化校验不证明业务结论正确；文件指纹刷新不代替语义复核。

## 2. 新知识的维护与冷启动（建议已整合入 Spec）

- 冷启动先建立最小团队底图：仓库、职责、业务能力、责任方、原始资料入口；缺失和未经确认的信息明确保留状态，不假装完整。
- 工具可从仓库元数据、接口与配置提取候选事实；业务含义、跨系统语义和隐性约定经相关责任方确认。当前不声称已实现自动底图生成。
- 用真实任务补全，选择一个经常跨仓协作的业务能力作为起点，不以全面覆盖或批量导入文档作为启用前提。
- Agent 在任务结束时提出三类结果：更新既有记忆、新增可复用记忆、无须沉淀；均说明理由和证据，减少使用者自行分类负担。
- 新记忆至少回答：解决什么反复出现的问题、归属哪个业务入口、已知结论与边界、证据、由谁确认；可先用正文表达，不预先增加大量强制字段。
- 为新增知识提供可发现的入口与引用，避免孤立卡片。优先由概念所属业务入口引用，勿为每种依赖复制完整正文。
- 简化生命周期可考虑：候选 → 已确认 → 待复核/有争议 → 更新或归档。具体状态名称、字段和自动行为尚待决定；勿与现有文件锚点状态混为一谈。
- 变更、使用中发现矛盾、原始依据失效时触发针对性复核；指纹变化只是其中一类信号。自动关联提醒仍需另行实现。
- 任务执行者提出草稿，相关业务或服务责任方审阅其范围内结论；避免让单一知识库管理员承担所有语义裁决。
- 可替代的重复内容合并；已失效内容撤出当前入口并保留历史；低使用量本身不构成删除高风险约束的理由。

## 3. 已纳入 Spec 的设计问题（具体自动化仍待实施）

- 任务何时触发沉淀，如何在价值不高时合理输出“无须更新”。
- 业务入口的粒度、重复与冲突识别、关系如何表达及保持可发现。
- 多服务关系由谁确认；未确认线索可以如何参与调查，不能如何充当决策依据。
- 业务代码、部署与知识生效的协同；共享记忆读到旧版本时如何暴露。
- 最小维护职责与复核信号；区分首期必需、后续自动化和试点后再决定的部分。
