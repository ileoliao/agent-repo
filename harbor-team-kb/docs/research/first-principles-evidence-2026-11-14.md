# Harbor Team KB：任务导航与团队知识的第一性原理证据

调研日期：2026-11-14。问题限定为：跨仓定位、理解业务、新人上手、遗漏约束与重复排障如何共同解释；在**不汇总全文、不建设全文搜索**的前提下，该保存什么。以下是研究证据与设计推论，不是产品已有效的证明。

## 1. 原始研究实际说明了什么

| 一手证据 | 观察或实验结果 | 对本项目的启发与适用边界 |
|---|---|---|
| Sillito、Murphy、De Volder，2006，[Questions Programmers Ask During Software Evolution Tasks](https://www.cs.ubc.ca/~murphy/papers/other/asking-answering-fse06.pdf) | 两项定性研究覆盖陌生代码的新人与熟悉代码的工业开发者，归纳 44 类问题：寻找初始落点、沿落点找关系、组织相连信息、整合不同局部模型。底层问题经常服务于更高层问题。 | 应围绕“要完成什么判断、下一步查哪里”组织导航；单个路径不等于完整理解。研究描述问题结构，没有试验某种知识库能提效，更不是现代跨仓 Agent 的能力测评。 |
| Ko 等，2006，[Seek, Relate, and Collect](https://faculty.washington.edu/ajko/papers/Ko2006SeekRelateCollect.pdf) | 探索性研究中，开发者交替寻找线索、沿依赖建立关系、收集稍后需用的信息；不准确的线索导致搜索失败，IDE 临时状态承载的线索会丢失并被重新寻找。 | 高价值记忆可包含经验证的调查入口、关系与验证办法。实验使用当年的 IDE 和陌生程序，不能把其导航时间比例直接套到今天，也不证明“目录卡”足以解决理解问题。 |
| Ko、DeLine、Venolia，2007，[Information Needs in Collocated Software Development Teams](https://www.microsoft.com/en-us/research/publication/information-needs-in-collocated-software-development-teams/) | 观察一家大公司的 17 名开发者，最常被延后获取的知识包括设计意图、预期行为和程序状态成因；唯一知情同事不可用会让任务搁置。 | 应保留“为什么、何时适用、谁能裁决、如何验证”，并允许有依据地求助。单公司的观察不能证明某项流程可普遍消除等待，也不能证明把专家全部知识写下来可行。 |
| Gloaguen 等，2026，[Evaluating AGENTS.md，v2](https://arxiv.org/html/2602.11988v2) | 对四种 Agent/model 组合、SWE-bench Lite 与 CTXbench 的比较中，额外上下文未显著提高解题率；自动生成文件平均成本增加 20%/23%。指令通常被遵循，却带来更多探索、测试；仓库概览未改善其定位指标。 | 直接反驳“补更多团队说明就会更好”的默认前提。主要是 Python GitHub issue 任务，不能推断私有跨仓导航或隐性业务约束无效；也不能声称文件越短就必然越好，论文未发现长度的显著影响。 |
| Liu 等，2023，[Lost in the Middle](https://arxiv.org/abs/2307.03172) | 在多文档问答与键值检索实验中，相关信息的位置会改变表现，长上下文中间的信息常较难被利用。 | “已经放入上下文”不等于“可靠使用”。这是较早模型及非编码任务的证据，不能直接证明当前 Agent 仍有同等缺陷，更不能推出某个固定 token 上限。 |
| Tan、Wagner、Treude，2024，[Detecting outdated code element references](https://link.springer.com/article/10.1007/s10664-023-10397-6) | 分析超过 3,000 个 GitHub 项目，发现文档中的代码元素引用会在源码删除后继续存在；自动发现后提交的问题促成部分修复。 | 可追溯关系与变化提醒能支持维护，但检测只针对一种过期形式。文件未变不能证明业务解释仍正确；文件变了也不等于约束失效。 |

## 2. 共同本质与可检验的因果模型

**设计推论：这些痛点可以共同表述为“任务所需的知识分散在代码、测试、业务裁决与人之间，执行者难以及时建立足够正确、适用且可检验的联系”。** 跨仓查找是入口成本，业务理解是关系与语义成本；遗漏约束是未知前提的风险，重复排障是已经付过的调查成本再次发生。它们相关，但不是同一个检索问题。

建议把下面这条链作为待验证的工作模型，而不是宣称已有研究证明的架构：

> 识别当前任务与未知项 → 对齐业务含义 → 找到相关载体和责任人 → 按需阅读、连接证据 → 核验适用条件及反例 → 实施并测试 → 只沉淀下次难以重新找到或重新推导的部分。

“像有经验的同事”应指这种工作方法：知道从哪入手、怎样查证、何时不能猜、何时问谁。无需模仿人脑存储结构，也不要求 Agent 预先拥有所有资料。产品定位可以是**帮助团队复用调查路径与业务判断依据**；薄卡只是实现手段，全文搜索、RAG、QMD 都不是该定位的必要组成。

据此，值得保存的内容不是固定的元数据清单，而是能让下一次任务少走弯路的最小交接：

- **可行动的入口**：业务说法对应哪个系统、哪个入口或测试，接下来如何验证，边界之外找谁。
- **证据之间的关系**：谁提供、谁消费，测试覆盖何种断言，哪个决定解释了看似多余的实现。只有仓名和路径仍可能无法回答任务。
- **难以现场还原的判断**：决策理由、隐含不变量、已知例外、故障触发条件及适用范围；保留原始依据和未确认项。
- **知识失效后的动作**：源码变化只是复核线索；权威来源不可达、运行参数缺失、裁决冲突时，应明确停止哪项推断、向谁补证。

这是价值筛选原则，不意味着复制所有调用关系或为每个函数制作卡片。能从当前源码和测试低成本重建的内容原则上留在原处；若某项关键语义能进一步成为类型、契约或测试，应让可执行载体承接它。

## 3. 对当前 Spec 的必要纠偏

以下均为本项目待验证的工程判断，不能借论文包装成定律：

1. “拿到路径后 Agent 很强、跨仓查找很弱”需要在团队真实任务上分开测。正确入口减少搜索空间，并不保证跨系统、动态参数和业务语义理解正确。
2. “80/20”、地图字符预算、门禁触发比例、试点达标百分比是本地策略，不是文献推导的最优值。“信息熵增规律”也不能充当文档双写容易过期的科学证明。
3. 不应普遍断言误召回比漏召回更贵：错误套用一条禁令和遗漏一条禁令都可能造成高损失。先区分任务与错误后果，再决定召回、核验和人工介入策略。
4. 新概念名不是独特性证明。可验证的差异应体现在：团队能否更快完成跨仓任务、更少基于错误前提行动，并在可承受的维护成本内保留这些收益。

## 4. 怎样证伪，而非只演示成功

以下为建议实验，尚未开展：选真实历史任务改写成未泄露答案的留出集，涵盖跨仓定位、解释一个业务行为、新人完成首个修改、识别被隐藏的约束、复现并避免旧故障，以及“资料不足必须求助”的案例。先冻结代码版本、工具权限与任务预算。

比较三组：A 为现有业务仓、文档与 `AGENTS.md + rg`；B 增加任务导航与求助路径；C 再增加少量隐性约束和决策依据。给各组相同原始资料访问权，随机或交叉分配任务，减少人员经验及重复做同一题的学习偏差；Agent 评测另行固定模型和配置，并重复运行以观察波动。

同时记录正确完成率、到达正确证据所需时间、业务解释及适用范围是否正确、是否遗漏关键约束、是否及时承认未知与求助、总耗时，以及知识维护耗时。由不知道实验组别的评审检查最终判断和证据链，不能只看是否命中预设卡片或修改了历史 PR 中同一文件。

历史缺陷归因可帮助选题；单纯上线前后缺陷下降无法排除任务难度、人员和流程变化。小样本试点足以发现明显无效或负担过重，但不足以承诺稳定的百分比收益。若 B/C 无增益，应删减导航或规则，而不是继续补卡直到演示命中。
