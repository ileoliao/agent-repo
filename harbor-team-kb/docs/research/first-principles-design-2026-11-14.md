# Harbor Team KB：从任务出发的设计定位与验证建议

日期：2026-11-14。状态：研究结论与设计建议，尚未通过团队真实任务验证；不替代现行 Spec，不表示以下能力已实现。

本次约束：跨仓定位、业务理解、新人上手、遗漏约束和重复排障都是痛点；不建设全文搜索，不把所有资料装入知识库，借鉴熟悉系统的人的工作方法。原始研究的具体结果与适用边界见[证据说明](./first-principles-evidence-2026-11-14.md)。

## 1. 本质问题与定位

**要解决的是：每个人、每个 Agent 接手陌生任务时，都在重复重建“这件业务怎样落在系统里、哪些判断有依据、哪些地方还不能确定”的上下文。**

知识本来就分散在代码、测试、需求、运行环境与人之间。把它们集中存放，不能自动消除理解成本；只给出文件路径，也不能自动形成正确的业务判断。

建议一句话定位：

> **Harbor 把团队已经走通的业务调查路径和关键判断依据交给下一位执行者，帮助人和 Agent 从业务任务走到可验证的行动。**

对外可称“团队工程导航与经验交接工具”。“海图”适合解释导航，但应明确图上还包括业务含义、关联依据、适用边界和求助路径。

这不是已被研究证明的产品架构。它是把研究观察转化成的可检验假设：减少重复定位、关系重建和业务求证的成本，同时控制误导与维护成本。

## 2. 从真实工作行为推导，而不是从存储技术推导

开发者研究反复观察到围绕任务寻找入口、连接相关信息、形成局部模型的过程；缺少设计意图或知情同事也会阻塞任务。这为保存调查路径、关系和求助入口提供了依据，但没有证明某种卡片格式能提效。[Sillito 等，2006](https://www.cs.ubc.ca/~murphy/papers/other/asking-answering-fse06.pdf)、[Ko 等，2006](https://faculty.washington.edu/ajko/papers/Ko2006SeekRelateCollect.pdf)、[Ko 等，2007](https://www.microsoft.com/en-us/research/publication/information-needs-in-collocated-software-development-teams/)

据此，建议采用以下工作循环：

1. **明确要作什么判断**：修改行为、解释异常、确认影响范围，还是学习一个业务能力。
2. **对齐业务含义**：术语指什么，有哪些同名概念，哪些任务条件会影响判断。
3. **找到初始落点**：负责的系统、实现入口、相关测试、需求依据及责任人。
4. **沿相关关系调查**：为什么还需要看另一个仓、它提供或消费什么、到哪里能验证。
5. **核对适用条件**：产品、合同群体、业务日期、环境、配置及例外是否匹配。
6. **区分事实与推测**：记录证据支持了什么，哪些仍未知，谁能补证或裁决。
7. **实施与验证**：读原始材料、运行测试、观察必要的运行数据，交付可检查结果。
8. **选择性沉淀**：只保留下次仍难以发现、推导或确认的路径和判断。

“模拟人”指借鉴这些可观察的策略。无需声称模拟人脑，也不应保留人的遗忘与过度自信。能由类型、契约、测试自动约束的规则，应进一步进入可执行载体。

## 3. 应该记住什么

### 3.1 长期共享的最小业务地图

| 内容 | 需要回答的问题 | 克制边界 |
|---|---|---|
| 业务概念与意图 | 这是什么，为什么存在，和相近概念有什么区别？ | 保留简短业务解释；不收录所有 PRD 和会议原文。 |
| 行动入口 | 去哪个仓、入口、测试或正式需求开始看？ | 给出“为什么看这里”；不人工复制整个调用图。 |
| 关键跨界关系 | 哪些系统共同完成这件事，接口之外有哪些语义约定？ | 优先记录从单仓和类型中难以看出的关系。 |
| 决策、约束与例外 | 为什么这样做，哪些前提不能丢，何时不适用？ | 必须有来源；示例说明判断，不替代完整试算集。 |
| 证据与求助路径 | 如何查证，缺什么，谁负责，冲突由谁裁决？ | 不把责任人名称当作已获批准，不把链接可达当作内容正确。 |

业务需求、功能需求当然属于这个模型：系统要达成什么、业务对象是什么、关键状态与不变量是什么，不能只留路径。具体实现分支、完整字段、实时参数和长篇论证留在原始载体，通过引用按需读取。

“薄”应表示有选择、有边界，而不是字数越少越好。对新人必要的两三句业务解释，往往比十个无说明链接更有价值。“80/20”只能是建设重心的比喻。

### 3.2 临时任务工作区

当前任务查到了哪些证据、正在验证什么、缺什么输入、下一步做什么，应有一个可恢复的小工作区。它服务于本次任务与交接，默认不进入长期共享知识。

只有经核实、可复用、值得承担维护成本的结果，才通过现有审阅流程晋升为团队记忆。整段会话、所有搜索结果和每次阅读记录不应自动回灌。

### 3.3 一条示意导航

以下是设计示例，不是已确认的 Harbor 业务事实：

> 任务：调整提前还款的费用处理。
>
> 先理解该能力处理什么，以及本次针对哪个产品与合同群体；从还款分配入口和既有用例入手。涉及账务消费时，再沿已说明的关系查看另一仓的契约测试。已知例外附上业务确认依据；新老规则按什么日期划分，必须核对正式定义。实际费率来自运行参数，Git 中没有当前值，需补工单输入或询问负责方。最后依据独立确认的样例验证修改。

这条导航保存的是调查的起点、转向理由和必须补齐的条件。执行者仍需现场阅读和判断；路径也允许随任务证据调整。

## 4. 信任模型：不能把“有来源”合并成“都是真值”

至少区分三类依据：

- **应当怎样**：已批准需求、正式业务制度及其适用范围。
- **目前怎样**：当前代码、实际部署版本、运行配置与观测数据。
- **为什么这样**：已确认的设计决策、历史例外与事故分析。

代码可能有缺陷，测试也可能复述同一个错误；获批需求可能尚未实现，当前主干也未必已部署。出现冲突时，保留冲突并按责任边界求证，不能自动以“代码优先”裁决所有问题。

现有文件指纹能提醒内容变化，不能证明业务理解正确或线上配置一致。不同合同群体可能同时适用新旧规则，因此“最新”也不能代替“适用”。无仓库、缺参数、缺批准依据、找不到负责方，都应成为明确的未知状态及后续动作。

## 5. 与 RAG 的边界应该怎么说

| 设计维度 | 常见文档问答型 RAG | 建议的 Harbor 核心 |
|---|---|---|
| 起点 | 一个待回答的问题 | 一个待完成的工程任务与待作判断 |
| 长期资产 | 可检索的文档及片段 | 业务概念、调查入口、关键关系、判断依据和求助路径 |
| 内容获取 | 检索相关文本并组织回答 | 按明确关系逐步读取原始载体、执行验证、补齐未知 |
| 主要产出 | 带来源的回答 | 足以推进任务、可核验的局部理解及下一步行动 |
| 成败标准 | 回答与引用质量 | 正确完成任务的成本、错误前提、求助和维护负担 |

这是常见产品形态的对照，不是 RAG 的技术能力上限。RAG 也可以检索路径、调用工具、支持任务；显式引用也会漏关系或指向过期内容。不能以“没有向量库”作为独特性证明。

本项目当前没有建设全文检索的需求。QMD 不进入核心方案；围绕概念入口与明确引用开展调查即可。现场使用 IDE、符号工具、`rg` 找代码仍属于正常调查，不要求预先汇总全文。已有卡片词匹配可作辅助入口，不能把“搜索命中更多卡片”当作产品价值。本次仅提出设计建议，未修改现有检索实现。

## 6. 已有先例与独特性的诚实判断

| 一手来源 | 已有能力或主张 | 对定位的约束 |
|---|---|---|
| [Mylar / Mylyn 原始研究](https://www.cs.ubc.ca/~murphy/papers/mylar/2006-11-mylar-fse.pdf) | 保存任务涉及的程序元素与关系，减少切换后重复寻找。论文报告 16 名自愿参与的工业开发者现场研究。 | “按任务组织上下文”已有长期先例；历史结果不能直接外推现代 Agent。 |
| [Microsoft CodeTour](https://github.com/microsoft/codetour) | 在代码中记录和回放带解释的导览步骤，可跨工作区文件夹并随仓库共享。 | “把老同事带新人读代码的路线留下来”已有直接先例。 |
| [Serena memories](https://oraios.github.io/serena/02-usage/045_memories.html) | 可审阅的 Markdown 记忆、按名称与引用逐步读取、引用完整性检查；明确偏好引用而非搜索。 | 不全文入库、渐进读取、Git 记忆均不独有。明确引用的目标可确定，不代表任务相关性必然正确。 |
| [Backstage Catalog](https://backstage.io/docs/features/software-catalog/) | 代码旁的元数据用于管理、发现软件资产及其归属。 | 仓库目录与 Owner 登记本身不是差异点。 |
| [Swimm 当前官方介绍](https://swimm.io/context-layer) | 宣称提供经专家核实的业务流程、规则、术语、跨仓影响及随代码选择性更新的上下文。 | 商业方案已覆盖大量相邻概念；这是厂商能力描述，不能当作独立效果证据。 |

**结论：方向合理，基础概念已有充分先例；尚不能声称独有或已有护城河。** 值得验证的具体组合，是在私有多仓与现有 Git 流程中，用较低维护成本交接业务语义、适用边界、现场查证和求助路径。

真正难复制的资产可能是团队长期核实过的跨仓业务关系与决策经验，以及它们随任务持续更新的机制。这仍是产品假设；如果静态导览加现有工具就能取得同等收益，额外引擎的价值需要重新审视。

## 7. 当前 Spec 应保留与修正的部分

保留：私有 Git 与公开工具分离、少量明确入口、引用原始载体、显式暴露锚点状态、人工审阅、高风险场景按需增加约束。

建议修正：

1. 从“导航坐标＋隐性禁令”扩充为“业务含义＋调查路径＋判断边界”。定位不应只照顾 Agent，也应让新人知道为什么读这些资料。
2. 给入口增加下一步查证理由、缺证后的动作与责任方。不要一次要求填满大量字段，只记录该任务真正需要的内容。
3. 区分业务意图、实现事实和决策理由，避免“唯一真值”掩盖冲突。
4. 把“准确路径之后 Agent 就能正确推演”列为待测假设，不作为产品前提。
5. 删除“信息熵增规律”的科学背书。双写增加同步负担是可观察的工程问题，不需要借用物理定律。
6. 不普遍断言误召回比漏召回更贵。误套约束与遗漏高损规则都可能昂贵；向量检索可以设置阈值，词匹配也不能保证适用。不选全文检索的依据应是任务范围与成本。
7. Story Guard 是可选的需求澄清出口，不能主导导航产品。哈希、结构检查与 Mock 测试不能证明需求语义、批准身份或真实 Jira 流程有效。
8. 门禁触发率、样本量、迭代数和缺陷下降百分比均是本地政策假设；不应包装成由研究推导的阈值。

本次未修改 `SPEC_V3.md`、`CORE_CONCEPTS.md` 或业务代码。

## 8. 如何验证这套设计值得存在

不能只用“卡片更短”证明有效。2026 年的 AGENTS.md 实验中，额外上下文未显著提高任务成功率，自动生成上下文反而增加成本；论文也未发现长度本身有显著影响。这不能证明私有跨仓知识无效，但要求我们正面验证增益。[Evaluating AGENTS.md，v2](https://arxiv.org/html/2602.11988v2)

### 最小试点

选一个跨仓业务能力，先从实际发生的调查中整理少量入口、关系和隐性判断。导航、证据与求助先行；不为完整覆盖去批量建卡，也不先开全团队门禁。

比较三组：

- A：现有仓库、原始文档、`AGENTS.md`、IDE 与 `rg`。
- B：A 加业务入口、调查关系与求助路径。
- C：B 加少量经确认的隐性约束、决策与例外。

各组能访问同样原始材料。使用不泄露解法的留出任务，冻结版本、权限与预算；按经验分层，随机或匹配分配任务。交叉实验不能让同一人重复做同题。Agent 单独固定模型配置并重复运行，避免把人员学习与模型波动当成工具收益。

### 场景与独立判定

| 场景 | 成功不是“读到了卡片”，而是 |
|---|---|
| 业务术语跨仓找实现 | 找到足够完成该任务的入口及关键关联，说明其作用。 |
| 解释一个业务行为 | 区分业务意图与实现，给出证据支持的因果解释。 |
| 新人首次修改 | 完成正确修改与验证，减少无效探索和返工。 |
| 隐性跨系统约定 | 识别相关单位、顺序、幂等或其他关键约束，并验证适用性。 |
| 旧故障再次出现 | 找到复现和判断依据；环境不同则不生搬历史结论。 |
| 新旧规则共存 | 根据正确对象与划断条件选规则，而非总取最新版本。 |
| 仓库缺失或引用变化 | 如实暴露未核验部分，继续查证或提出有效求助。 |
| 代码不变、线上参数变化 | 不把指纹一致当作业务事实未变，补齐运行输入。 |
| 正式需求与实现冲突 | 显式列出冲突、影响和裁决路径，不擅自抹平。 |
| 完全陌生的业务 | 承认地图未覆盖，找到合适入口或负责方，不编造确定结论。 |

由领域负责人预先确定独立的正确性依据，条件允许时让评审不知道实验组别。历史 PR 改过的文件和既有测试都只是证据之一，不能独自充当标准答案。

记录正确完成率、获得有效证据的时间、关键关系与约束遗漏、错误前提、总耗时和返工；同时记录有效求助、被打断同事的投入、每周维护时间及变化提醒误报。不能通过一直求助或停止执行来刷“安全率”，必须同时看实际完成能力。

小样本可以淘汰明显无效或负担过重的方案，不能支持稳定的缺陷下降百分比承诺。若 B 已足够，避免扩张 C；若 B/C 不优于 A，应删减或重新设计，而不是继续堆卡。收益判断应覆盖执行成本、误判损失和长期维护，不能只看一次演示节省的搜索时间。

## 9. 推荐的近期决策

先把“从业务任务到可验证行动”的路径做清楚，并用真实任务验证。长期共享记忆保持有选择的业务模型与调查经验；详情留在来源处，临时调查留在任务里。QMD、全文入库、大规模自动知识图谱与普遍门禁都不构成当前核心的必要条件。

这套方案成立的证据，应是下一位同事或 Agent 能以更低总成本形成正确判断并完成任务，而不是知识库拥有多少内容。
