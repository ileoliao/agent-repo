This is the detailed view behind the previous slide. Top: two kinds of callers. In the browser, an extension runs in a sandboxed iframe with no network access of its own; it calls the harbor.js SDK, which hands the request to the portal over postMessage, and the portal sends it with the user's session cookie. The CLI and Copilot agents send a PAT directly. Middle: every request hits the same gateway route, /gw/{connector}/{path}, and passes six steps. One, authenticate: the PAT service introspects the cookie or PAT, cached for 60 seconds. Two, resolve: the method and path are matched to a capability, and path tricks like dot-dot or encoded slashes are rejected. Three, authorize: the user's AD groups, the capabilities the extension declared, its visibility, and for writes the platform team's grant must all allow it; otherwise the gateway denies with a readable reason. Four, rate limit per user, extension and connector. Five, forward the request unchanged, adding only the connector's service credential and a signed identity token valid for 60 seconds, so downstream sees the real operator. Six, audit every decision. Bottom: built-in connectors use a service account; team-built services like outage are identity-only, verify the token, and keep their own business rules. Right: the control plane is Git. Connectors, extensions and grants are YAML in the repo; CI lints and validates, merge publishes, and the gateway hot-reloads. The PAT service is the only external dependency; credentials live only in the gateway; audit goes to OTel. The platform stores no business data.
